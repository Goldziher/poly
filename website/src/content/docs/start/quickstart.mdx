import { Aside, Steps, Tabs, TabItem, Code, LinkCard, CardGrid } from '@astrojs/starlight/components';

polylint needs no configuration to be useful. Point `poly` at a repository and it works out what
each file is and which engine should handle it.

<Steps>

1. ## Lint everything

   ```console
   $ poly lint
   ./app.py
     warning  ruff  T201  5:5  `print` found
     warning  ruff  ANN201  4:5  Missing return type annotation for public function `main`
     error  ruff  F401  1:8  `os` imported but unused

   3 issues found.
     2 files linted
     1 issue fixable with the `--fix` option
   ```

   Only the `error` line fails the run. Warning-severity findings — the code-quality tier, opt-in `typos` (`[engines.typos] enabled = true`),
   and the widened rule selections — never redden CI on their own.

   <Aside type="note" title="The first run downloads engines">
   Except on the bundled Linux musl build, the first run downloads the engine components for
   the languages it finds — here `python` among them — plus any tree-sitter grammars it needs, verifies
   each against the signed lock embedded in the binary, and caches them in the per-user cache
   directory. Later runs download nothing. `poly components status .` shows what a directory
   needs; `--offline` forbids downloads. See
   [Components and offline use](/poly/guides/components/).
   </Aside>

2. ### Check formatting

   ```console
   $ poly fmt
   would reformat ./src/main.rs

   1 file will change.
     2 files checked
   ```

   `poly fmt` is a **dry run by default**, which is what a CI job wants. There is no `--check`
   flag; `--fix` is what writes.

3. ### Apply changes

   <Tabs>
   <TabItem label="Formatting">
   <Code
   code={`$ poly fmt --fix\nreformatted ./src/main.rs\n\n1 file reformatted.\n  2 files checked`}
   lang="console"
   />
   </TabItem>
   <TabItem label="Lint autofixes">
   <Code code={`$ poly lint --fix`} lang="console" />
   </TabItem>
   </Tabs>

4. ### Wire the git hooks

   ```console
   $ poly hooks install
   ✓ Installed 2 git hooks in .git/hooks
     › commit-msg
     › pre-commit
   ```

   Lint, format and Conventional-Commit checks now run on every `git commit`, with no external
   hook framework in between.

</Steps>

## A first `poly.toml`

Everything above works with no config at all. Add one when you want to change poly's opinions:

```toml title="poly.toml"
[defaults]
line_length = 120
line_ending = "lf"
final_newline = true
trim_trailing_whitespace = true

[discovery]
exclude = ["vendor/**", "fixtures/**"]

[engines.ruff]
extend_select = ["D"]

[hooks]
stages = ["pre-commit", "commit-msg"]

[hooks.builtin]
lint = true
fmt = true
commit = { stages = ["commit-msg"] }
file_safety = true
```

`poly.local.toml` layers machine-local overrides on top, and nested `poly.toml` files cascade in a
monorepo. See [Configuration](/poly/guides/configuration/) for the full surface.

<Aside type="tip" title="Already have a pile of tool configs?">
    `poly migrate` reads your existing `ruff`, `taplo`, markdownlint and `typos` configs (including
    `pyproject.toml`'s `[tool.ruff]` / `[tool.typos]` / `[tool.codespell]`), plus a `lefthook.yml`
    or `.pre-commit-config.yaml`, and folds what it can honor into `poly.toml`. It is a dry-run
    report by default; `--write` applies it.
</Aside>

## Exit codes are a contract

| Code | Meaning |
| ---: | --- |
| `0` | Clean. |
| `1` | Error-severity findings, a failed whole-project tool, or (for `poly fmt`) files that would change. |
| `2` | The run verified less than it claims — a file an engine failed on, a skip budget exceeded, a config error, or a report that failed to serialize. |

<Aside type="note" title="`poly fmt --fix` exits 0 when it rewrites">
    In fix mode, rewriting files is success. Add `--exit-nonzero-on-fix` for a CI step that must
    fail when the committed tree was not already formatted (`poly fmt --fix --exit-nonzero-on-fix`
    then exits `1` after rewriting).
</Aside>

A `--format json` or `--format toon` consumer must check the **exit code**, not just the payload:
the whole-project phase's own pass/fail is written to stderr so that stdout stays a single valid
document.

## In CI

```yaml title=".github/workflows/ci.yaml"
name: lint
on: [push, pull_request]

jobs:
  poly:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Goldziher/poly@v0
        with:
          components: auto   # pre-install and cache the components this repository needs
      - run: poly fmt .
      - run: poly lint --deny-skips .
```

`--deny-skips` turns a skip that is a limit of poly — no matching engine, no lint rules for the
language, a generated-file skip, a binary file — into an exit-2 failure, so the job cannot quietly
stop covering part of the tree. A skip that names a caller instruction (`--only`/`--skip`,
`enabled = false`) is never charged; see
[Coverage and withdrawal](/poly/guides/configuration/#coverage-and-withdrawal). Use
`--max-skips <N>` if you have a known, budgeted set of charged skips.

Add `-q` on a large repository to trim the per-file discovery detail; every count and reason still
appears in the summary.
